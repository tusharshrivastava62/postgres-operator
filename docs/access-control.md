# Access control

This page covers who can log in to a cluster's databases, and how: the read-only role the operator's
own jobs use, the database roles for your applications, how their passwords are stored and replaced,
and temporary superuser access for an emergency. Everything here is configured in the cluster's
spec and reported in its status. Nothing needs to be run by hand in the database.

Throughout, "the operator connects as the superuser" means: over TLS, to the primary, on port 5432,
with the password in `<cluster>-credentials`. The server's certificate is generated by the image and
is not verified (that belongs to the security hardening work). It is encrypted, not authenticated.

## The read-only role for the operator's own jobs

A cluster with backups or a compliance preset runs small jobs that read the database: the backup
status check and the compliance check. They connect as a role called `pgoperator_monitor`, not as
the superuser, so **no job pod holds the superuser's password.**

| | |
|---|---|
| Role | `pgoperator_monitor`, a reserved name |
| Secret | `<cluster>-monitor`, with `username` and `password` |
| Can | read the server's settings (`pg_read_all_settings`), read the connection rules, and ask how many roles have a password that is not stored as SCRAM-SHA-256 |
| Cannot | read any table, read password hashes, see other sessions' queries, read files, run programs, create anything, become another role |
| Made | when the cluster has backups with a destination, or a compliance preset; on the first reconcile with a primary |

It does not use `pg_monitor`, because that includes the right to read other sessions' query text. The
one thing it needs from the password table, a count, goes through a function that returns only the
count.

The operator logs in as the role itself to check it, and uses the superuser only to put it right: when
it is missing, has a changed password, or has lost a privilege. A role found in order is trusted for
five minutes. Its state is in `.status.accessControl.monitorRole`.

## Database roles for your applications

```yaml
spec:
  roles:
  - name: app_orders
    database: orders          # created for the role to own
    connectionLimit: 20
    rotateEvery: 2160h        # optional; see "Replacing passwords"
  - name: reporting           # a login with no database of its own
```

See [`config/samples/db_v1alpha1_postgrescluster_access.yaml`](../config/samples/db_v1alpha1_postgrescluster_access.yaml).

**What a role is.** It can log in, and that is all: not a superuser, and unable to create roles or
databases, replicate, or bypass row security. If it has a `database`, it owns that database, and
everyone else is refused connection to it. What the role creates inside its database is its own
affair; there is no way to grant more through the spec.

**What the operator does.** For each role it generates a password, writes it to a Secret, creates the
role and the database, and keeps them as the spec says, reading the database every few minutes and
whenever the spec or a Secret changes. It sends the database a SCRAM-SHA-256 hash of the password, never
the password: the server logs the statement that sets it, so a clear-text password would be in the log,
and in the audit bucket.

**The Secret** is `<cluster>-role-<role>`, with underscores in the role name written as hyphens, unless
`secretName` says otherwise. It has `username`, `password`, `host` (the read-write Service),
`port` and, if there is a database, `dbname`. It is not deleted with the cluster or with the role, for
the same reason the cluster's own credentials Secret is not: the password is in the database, which
outlives the cluster with its volumes. If the Secret is deleted, the operator writes a new password and
sets the role to it.

**Names.** A role name is lower-case letters, digits and underscores, starting with a letter. It may not
start with `pg_` or `bg_`, and may not be `postgres`, `replicator`, `admin`, `cron_admin`, `robot_zmon`,
`zalandos` or `pgoperator_monitor`. A database may not be `postgres`, `template0` or `template1`, and
only one role can name a database. A role's Secret may not be one the operator makes or one the spec
points at for backups, restores or audit logs. The webhook refuses all of it, and the controller
checks again when the webhook is not there (`Progressing` says `InvalidRoles`).

**What it will not touch.** A role of the same name that the operator did not make is reported as an
`Error` and left alone, like a database that already exists with another owner, or a Secret of the
right name that is not the operator's. The operator marks every role it makes with a comment, and only
alters roles that carry it.

**Taking a role out of the spec disables it. It is never dropped.** Its login is turned off and its
sessions are ended, and it is listed in status as `Disabled`. The role, its data and its Secret stay,
because a role that owns tables cannot be dropped, and a drop is not something to do on a change to a
YAML file. Drop it yourself when you are sure. Adding it back turns its login on again with the
password in its Secret. A database a role stops naming is likewise kept.

**Status.** `.status.accessControl.roles` lists each role as `Ready`, `Pending` (no primary yet),
`Error` (with the reason) or `Disabled`, and the `RolesReady` condition is true when every role in the
spec is `Ready`. The metric `postgrescluster_roles` counts them by state.

**A restored cluster** holds the roles of the cluster it came from, with that cluster's passwords. The
operator takes over the ones in its own spec and sets new passwords, and disables the rest, even if the
spec lists no roles. It does this for any cluster with `spec.bootstrap.recovery`.

## Replacing passwords

Passwords are replaced when someone asks, and, if the spec says so, on a schedule. **They are never
replaced unless you ask for it one way or the other.**

**Asking.** Annotate the Secret that holds the password with any value you have not used before:

```bash
kubectl annotate secret orders-role-app-orders db.youroperator.io/rotate=ticket-1234 --overwrite
```

The operator answers once for each value, and records it (`db.youroperator.io/rotated-token`) with the
time (`db.youroperator.io/rotated-at`) on the Secret. The same works on `<cluster>-monitor` and on
`<cluster>-credentials`.

**Scheduling.** `rotateEvery` on a role, and `spec.credentialRotation.monitorEvery` and
`.superuserEvery`, replace a password when it is older than that. At least `24h`. A password's age
is the time on its Secret's `rotated-at` annotation, or, if it never was replaced, the Secret's age.

| Credential | How | What it costs |
|---|---|---|
| An application role | The new password is set in the database, and then written to the Secret | New connections made with the old password are refused until the application reads the Secret again. Open connections are not affected. |
| The monitor role | The same | A job that started a moment earlier may fail once; the next run is right. |
| The superuser and the replication role, together | See below | A rolling update of every pod: replicas first, a switchover, then the old primary. About two seconds of refused writes. |

**An application that reads its password once, when it starts, is refused after its password is
replaced** until it is restarted. That is the cost of one password per role. Rotate on a day you can
restart the application, or have it re-read the Secret when a connection fails. If you need no gap at
all, the answer is two roles that take turns, which the operator does not do.

**The superuser and replication passwords** are used by every pod: Patroni reads them from its
environment when it starts, and a pod that starts with passwords the database does not have never
becomes ready. So the operator:

1. writes the new passwords to the credentials Secret as `password-next` and `replication-password-next`;
2. sets them in the database, in one statement, as hashes; if it stops here it finds out which password the
   database accepts, and carries on from there;
3. in one change to the Secret, makes them the passwords, removes the `-next` keys, and raises
   `db.youroperator.io/credentials-version`.

That version is on the pod template, so step 3 starts the rolling update that gives every pod the new
passwords. A rotation waits, and says why in `.status.accessControl.credentials`, while the cluster is
not healthy or is already being updated. One that has begun is finished whatever the cluster looks like.
A pod that restarts by itself between steps 2 and 3 with the old passwords does not become ready until
the rolling update replaces it, which it is about to.

**Status and metrics.** `.status.accessControl.credentials` says `Idle`, `Waiting`, `Rotating`,
`Rolling` or `Error`, with the reason, and when the passwords were last replaced. The roles and the
monitor role show the same in `lastRotated`. `postgrescluster_credential_age_seconds{kind}` is the age of
each kind (`superuser`, `replication`, `monitor`, `application`, the oldest role), so a password nobody
has replaced in a year can be alerted on.

## Emergency access

Temporary superuser access for an emergency, requested, recorded and ended by the operator. **Read
[emergency-access.md](emergency-access.md) first: the statements of an escalated session, and the values
bound to their parameters, are written to the server log in clear text.**

## Upgrading from 0.1.0

On the first reconcile after the operator is upgraded, a cluster with backups or a compliance preset gets
the `<cluster>-monitor` Secret and the `pgoperator_monitor` role, and its jobs switch to them. A
network policy gains the rule that lets the operator reach port 5432. No database pod is replaced, no
existing password changes, and the superuser's and replication passwords are not touched unless you ask.
The new `PostgresEmergencyAccess` CRD has to be applied (`kubectl apply -f charts/postgres-operator/crds/`
for a Helm install), and the chart adds a mutating webhook.

## What this does not do

- It does not make the connection authenticated: the server's certificate is not verified.
- It does not restrict the replication role, which can log in as an ordinary client, or give `pg_rewind`
  a user of its own. Both belong to the security hardening work.
- It does not give an application a way to keep a connection across its password being replaced, or
  rotate the password of a role you made yourself.
- It does not grant a role anything beyond a login and its own database. Grants are yours to make.
- It does not drop what it disables, or tell you when a Secret is read: the Kubernetes audit log does.
- It does not check any of this for you against a regulation. See
  [compliance.md](compliance.md) for what a preset does and does not do.
